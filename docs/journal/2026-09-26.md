## 🚧 Challenges & Solutions

### 1. SPM Package Name Discrepancy Blocking Clean Downstream Integration
- **Problem**: When integrating `AppCore` in Xcode and nested SPM tooling, dependencies failed to resolve due to `package: "system-one-laya"` being declared while the root package was named `SystemOneFoundationModels`.
- **Solution**: Standardized the package identity to `SystemOneFoundationModels` in `AppCore/Package.swift`, aligning target dependencies and package manifests.

### 2. Outdated Tech Note Cross-References Misleading Engineers
- **Problem**: Multiple production files referenced outdated tech note slugs (e.g. `0002-coreml-shape-discrepancy.md` instead of `0002-coreml-runtime-quirks.md`, and non-existent `0003` variants), creating broken links and confusion when diagnosing Core ML and App Check behaviors.
- **Solution**: Conducted a repository-wide grep for `tech-notes/`, audited against the canonical index in `tech-notes/README.md`, and updated all inline source comments and documentation links.

### 3. Getting-Started Guide Presenting Artificial Onboarding Paywall
- **Problem**: Developers reading `docs/getting-started.md` were greeted with mandatory instructions to obtain a TypeSafe API key before running any code, obscuring the library's flagship feature: 100% offline, zero-cloud on-device Core ML inference.
- **Solution**: Restructured the guide into a "Choose Your Path" matrix that puts on-device Core ML and self-hosted `laya-serve` front and center as zero-cost, zero-key options, while cleanly positioning hosted Jev cloud inference as an opt-in choice.

### 4. Fragmented Example Discoverability
- **Problem**: The repository featured 5 powerful examples across CLI and full SwiftUI apps, but lacked a cohesive root catalog explaining which example demonstrates which architectural pattern (Dynamic Profiles, offline Core ML, RFC 9110 retries, etc.).
- **Solution**: Created `Examples/README.md` with a comprehensive feature matrix and standardized quick-start execution commands.

## 📌 Key Decisions

### 1. "Choose Your Path" Tri-Modal Onboarding Architecture
- **Context**: The library unifies both cloud-based Jev decision models and on-device/local Laya models under Apple's Foundation Models framework. Presenting a single sequential onboarding guide misled developers into believing cloud accounts were required.
- **Decision**: Structurally bifurcate onboarding into three distinct paths (On-Device Core ML, Local `laya-serve`, and Cloud Jev) in `docs/getting-started.md`. Emphasize zero-dependency offline onboarding first.
- **Alternatives Considered**: Maintaining separate documentation websites for Jev and Laya (rejected: defeats the value of a unified bridge conforming to standard `LanguageModelSession`).

### 2. Package Identity Alignment (`SystemOneFoundationModels`)
- **Context**: Historical renames from `system-one-laya` left dangling package names in `Examples/MailTriageApp/apps/apple/Packages/AppCore/Package.swift`.
- **Decision**: Enforce `SystemOneFoundationModels` as the singular authoritative SPM package identity across all manifests and documentation.
- **Alternatives Considered**: Aliasing package names (rejected: creates brittle build configurations and obscures SPM dependency graphs).

### 3. Zero-Key Offline-First Developer Contract (`CONTRIBUTING.md`)
- **Context**: New contributors need clear expectations around test execution and CI reproducibility without needing private company secrets.
- **Decision**: Codify in `CONTRIBUTING.md` that `swift test` must pass 100% offline without any API keys or network calls. Require mocks (`MockSystemOneBackend`, `MockJevTransport`) for protocol and serialization validation.
- **Alternatives Considered**: Mocking at the network HTTP transport level via third-party libraries (rejected: violates zero-external-dependency rule).

### 4. Centralized Examples Catalog & Target Decision Matrix
- **Context**: Developers frequently ask which of the 4 library targets (`SystemOneFoundationModels`, `LayaFoundationModels`, `LayaOnDevice`, `JevFoundationModels`) they should import.
- **Decision**: Publish an explicit "Which Target Should I Import?" decision matrix in the root `README.md` and `docs/getting-started.md`, accompanied by a unified `Examples/README.md` cataloging all reference code.
- **Alternatives Considered**: Relying purely on API docstrings (rejected: architectural decisions happen before opening the code editor).
